# Renovate Upgrades

Safely upgrade this homelab one Renovate PR at a time. Use `gh` for every GitHub operation. Treat a deployed upgrade as complete only after Flux and its target workload reach the expected state.

## Scope

Accept a PR only when all of these are true:

- Its author is the Renovate GitHub App `app/renovate-bot-gravity182` and the author is a bot.
- Its diff is a dependency update generated by Renovate.
- It upgrades one of these targets:
  - deployed applications or platform components under `kubernetes/`;
  - GitHub Actions;
  - locally managed development tools.

Treat every other PR as out of scope, including non-Renovate PRs, Renovate configuration changes, and any PR touching `talos/`. Do not inspect, plan, or merge an out-of-scope PR. List it with the reason it was excluded. If an otherwise eligible PR also touches an excluded path, exclude the whole PR.

## Safety rules

- Inspect every eligible PR completely before proposing it for merge.
- Require explicit user approval after presenting the merge plan and before every merge batch.
- Process approved PRs serially. Verify the current PR before merging the next one.
- Re-check the exact head SHA, mergeability, and required checks immediately before merging.
- Merge only with `gh pr merge <number> --squash --match-head-commit <head-sha>`.
- Do not use `--admin`, bypass checks, resolve conflicts, delete branches, force reconciliation, or delete cluster resources.
- Stop and report the blocker when a check, diff, release note, compatibility assessment, or verification result is unclear or fails. Do not invent a workaround.

## Review and plan

1. Confirm the repository, `gh` authentication, squash-merge availability, and working-tree state. Preserve user changes.
2. List open PRs and apply the scope gate before doing detailed review.
3. For each eligible PR, use `gh pr view`, `gh pr diff`, and `gh pr checks <number> --required` to inspect its metadata, exact head SHA, complete diff, mergeability, required checks, and review state.
4. Confirm the diff contains only the expected dependency update. Read applicable release notes, breaking changes, migration notes, and surrounding manifests.
5. Classify the update:
   - **Deployed application or platform:** derive the affected Flux resource, namespace, workload, and version or image expected after reconciliation.
   - **GitHub Action or local tool:** derive the relevant configuration and check that proves the update is valid. Do not claim a cluster deployment occurred.
6. Before any deployed upgrade, record node readiness and the relevant Flux source, Kustomization, HelmRelease, and workload state. Identify pre-existing failures separately. Do not merge when the target is already unhealthy.
7. Present the serial merge plan with each PR's head SHA, upgrade, compatibility findings, checks, verification target, and decision. Exclude out-of-scope PRs explicitly.
8. Request approval. Approval applies only to the listed PRs at their listed head SHAs. Request fresh approval if a SHA, check, merge state, or material finding changes.

## Merge and verify

For each approved PR:

1. Re-fetch its state, required checks, mergeability, and head SHA. Stop if any no longer match the approved plan.
2. Merge with squash and `--match-head-commit`.
3. For a deployed upgrade, wait for normal Flux reconciliation. Do not force it. Verify the expected Git source revision, affected Kustomization or HelmRelease, and target workload.
4. Prove the update reached the intended version:
   - image or digest: selected pods use the expected image or digest and the rollout is complete;
   - Helm or OCI chart: source or HelmChart resolves the expected version, HelmRelease is Ready, and the primary workload is ready;
   - network, storage, operator, or CRD component: component health, target workload, and node readiness are good, with required migrations addressed.
5. For a GitHub Action or local-tool upgrade, verify successful checks and the changed configuration. Do not perform cluster verification.
6. Stop the sequence if Flux, the target workload, or the required validation fails or degrades. Collect relevant status and events; do not merge the next PR.

## Report

Report merged PRs with their reviewed SHA, merge commit, upgrade, and verification result. Separately report excluded and blocked PRs, pre-existing cluster failures, and any failure that halted the sequence.
